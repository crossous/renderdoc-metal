# BATCH131–132：非重叠 Heap 资源 makeAliasable

`MTLBuffer::makeAliasable` 与 `MTLTexture::makeAliasable` 现在通过 wrapper 捕获为
对应旧 chunk，回放校验身份、类型和 heap 归属后再调用 Metal。帧内调用保留资源
引用；帧外调用附到资源记录。T131/T132 分别对独立的 automatic-heap buffer/
texture 在所有 GPU 工作完成后标记 aliasable；原生 Metal Validation 检查
`isAliasable()`，捕获中的 chunk 位于最终 wait 后，API 验证 heap→子资源关系、
原有 GPU 数据/画面及事件回退。每份捕获拒绝 3 个畸形目标（空、错类型、非 heap）。

终端入口：

```sh
bash util/buildscripts/scripts/test_metal_capture_batch131_132_macos.sh
RENDERDOC_METAL_LAST_TEST=132 bash util/buildscripts/scripts/test_metal_replay_batch35_38_macos.sh
```

边界很重要：本批只证明**标记后不再使用、也没有后续重叠分配**的生命周期。
Placement heap 的同一地址重叠资源、automatic heap 复用先前内存，以及帧内
`makeAliasable` 与新资源创建的严格时序，仍由独立门槛处理；现有 placement replay
仍拒绝重叠范围。不能把本批记作完整的 heap alias/reuse 支持。

T133 是此门槛的原生反例：placement buffer 在一次提交后 `makeAliasable`，随即在
相同 offset 建立新 buffer，第二次 compute/copy 的 516-byte 结果在 Metal Validation
下正确；注入捕获也成功。但初始资源记录会把第二次分配提前到 frame 前，现有
回放**明确拒绝** `MTLHeap::newBuffer(offset)`。尝试把创建保留在帧内后还发现
ReplayLog 的重复执行需要重新建立 alias 前的 heap 状态，否则初次加载后 seek/预览
会失败；试验性改动已撤回。复现入口：
`bash util/buildscripts/scripts/test_metal_alias_reuse_rejection_macos.sh`。
