# BATCH104–105 — Dynamic library linked execution

`Metal_Dynamic_Library` builds a dynamic MSL source library, creates
`MTLDynamicLibrary`, serializes it, compiles an executable MSL library with
the dynamic library in `MTLCompileOptions.libraries`, then runs a linked
compute kernel and draws its output. T104 uses one dependency and expects
`float 3`; T105 uses two different dynamic libraries and expects `float 6`.
Both produce a red center pixel. Metal API Validation confirms native
execution, capture, CLI replay and Replay API readback. The replay wrapper
recompiles dynamic MSL with a fresh private install path and materializes
the recreated dynamic library there before compiling the executable. The
original application path is never reopened by replay; a mutated capture
pointing to a nonexistent source install path still replays.

The device `newDynamicLibrary:` bridge and old chunk are now handled.
Source-library capture version 6 stores library type, install-name metadata,
dependency resource IDs and an explicit support bit. Replay accepts only a
bounded, known compile-options subset and validates identity and dependency
types before native creation. The executable's resource record depends on
every dynamic library, so replay initialization retains creation order.
`newDynamicLibraryWithURL:` remains unsupported: a native probe showed that
moving a serialized metallib and importing it from the new URL preserves
its original embedded install name; pipeline linking then fails if that
original path is absent. An arbitrary original path must not be written
during replay just to remove this marker. At this checkpoint async source
compilation with dynamic options, more complex compile options and more
than eight dependencies remained unsupported. The dynamic async subset
was subsequently added in [BATCH110–111](BATCH110-111.md).
