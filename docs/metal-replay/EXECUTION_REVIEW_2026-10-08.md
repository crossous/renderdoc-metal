# Metal 重放开发复盘与执行改进方案

日期：2026-10-08。用途：交给主对话采用的工程计划；规划采用较高推理深度，实际开发继续由 Sol high 执行。

本次侧对话只阅读仓库并新增本文及配套 prompt，没有改后端、测试、现有执行规则或持续任务配置，没有运行构建/GPU 测试。本文的历史 PASS/FAIL 均转述已保存记录，不构成本次重新验收。主对话采用时先核对最新源码和状态，再整合执行规则，避免覆盖正在进行的修改。

## 1. 评估结论与当前基线

主要问题是通用恢复机制建设滞后，同时将过多 CPU 分析结论用作重放前提。早期以小 sample 为边界的格式、尺寸、绑定及调用限制逐步变成生产准入条件；增加新负载后，需要反复扩大这些条件。最近已完成部分整改，但更换场景仍可能触发同类问题。

并非此前工作没有价值：捕获包装、AS 构建输入、Private 初态、提交快照、真实 Native query、地址重定位、事件往返及独立样例验证都应保留。也并非完全没有参考 DX12/Vulkan。问题是部分参考停留在局部接口和检查方式，尚未充分落实为资源管理、原生执行和可选访问展示的职责划分。没有足够证据给出各原因的时间占比。

基线以本次读到的最新完成记录为准：

- 最新记录候选 backend/bundle 为 568e50eb（2026-10-08，API 创建初态修复）。该候选未重复运行不受本次修改影响的 UE 预检，不继承旧候选结果为通过。
- UE 捕获 403f90ea 已记录真实 RT：119 个 compute PSO 完成 metadata/AIR 核对，6 个 query PSO，5 次非零 query 调度；这证明捕获包含 RT，不能证明重放正确。
- 最近一次相关 UE 预检记录属于 c573bda0：禁用初态上传和 frame GPU，仍因动态候选 buffer14714 的内容/producer 义务拒绝。它是 heap placement buffer；新 device buffer 的创建初态规则不适用。没有证据说明该候选被 shader 实际读取。
- UE 整帧 GPU 输出、事件往返/EID0、绑定及最终集中能力验收尚未完成，两个生产 RT 能力开关仍为 false。

后续状态更新以后续证据为准，不以本文哈希冻结主线。依据：[最新状态](STATUS.md)、[通用恢复记录](GENERIC_API_RECOVERY.md)、[UE RT 捕获范围](BATCH544_API_RT_INTEGRATION.md)。

## 3. 将“参考 DX12/Vulkan”变成设计约束

每个能力批次只维护一张简短对照卡，在机制改变时更新，不要求每个小补丁重复写长篇对照。对照必须覆盖同一问题的完整数据流，而不是只列函数名。

| 职责 | 本仓库参考入口 | Metal 应复用的设计 | 必须单独确认的差异 |
|---|---|---|---|
| 内存与初态 | D3D12ResourceManager::Prepare_InitialState / Apply_InitialState；WrappedVulkan::Prepare_InitialState / Apply_InitialState(eResDeviceMemory) | 捕获时间点、物理 backing、逻辑投影与恢复区间分开；alias 不复活过期初态 | Metal 可合法访问/复制的 buffer 范围、texture/AS opaque footprint、创建 API 初态契约 |
| descriptor/地址 | D3D12Descriptor::GetRefIDs、GetResIDFromAddr、CopyDescriptorsSimple；Vulkan buffer address 与 BindBufferMemory 路径 | 保存资源身份、offset、版本和绑定；重建重放对象/地址 | Metal 原始编码表、gpuResourceID、converted ABI；Vulkan 部分地址机制不能机械照搬 |
| 原生执行 | Serialise_Dispatch；Serialise_vkCmdDispatch | 恢复对象和绑定后调用原 Native API，保留真实参数与顺序 | GPU 生成 descriptor/地址需要保证结果属于重放地址空间 |
| 提交依赖 | Serialise_ExecuteCommandLists；Serialise_vkQueueSubmit | 按 API 命令、等待关系及原上传时间恢复；未来写入不能补过去读取 | Metal encoder/command buffer、hazard/alias 的具体语义 |
| 检查与展示 | 两后端 GetDescriptorAccess / shader feedback | 展示可为部分或未知，不能虚构实际访问；与原生调度职责分开 | 没有等价反馈机制时如实记录限制，无需先完成逐 invocation 分析 |

源码位置：[DX12 初态](../../renderdoc/driver/d3d12/d3d12_initstate.cpp)、[Vulkan 初态](../../renderdoc/driver/vulkan/vk_initstate.cpp)、[DX12 调度](../../renderdoc/driver/d3d12/d3d12_command_list_wrap.cpp)、[Vulkan 调度](../../renderdoc/driver/vulkan/wrappers/vk_draw_funcs.cpp)、[DX12 展示](../../renderdoc/driver/d3d12/d3d12_replay.cpp)、[Vulkan 展示](../../renderdoc/driver/vulkan/vk_replay.cpp)。

对照卡回答五件事：捕获保存什么、恢复时如何得到同等输入、地址如何处理、依赖如何保持、可选分析失败是否影响 Native 执行。若 Metal 的拒绝在对应后端不存在，应解释具体 API 差异或尚缺的恢复机制，并给出移除临时限制的条件。驱动规避、硬件限制和协议兼容可以保留；不得将其泛化为按引擎功能名称授予支持。

## 4. 核心整改：定义正确的恢复义务

### 4.1 独立维护五类事实

以下是职责划分，不要求一次引入新的通用框架或重写全部代码。可以逐步整理现有结构，使字段与返回结果含义明确。

1. 对象/内存：真实资源、物理 backing、范围、别名、生存期、当前 generation。
2. 地址：当前字段的布局、资源身份+offset、发布版本，以及 captured→replay 地址修复。
3. 执行输入状态：捕获初态、创建 API 原输入、帧内原命令生成的内容、API 未指定的内容、确实丢失的必要数据。
4. 提交依赖：哪些命令必须执行，哪些上传/发布在本次消费前生效，seek/EID0 如何重建。
5. 可选分析：CPU 数值、可能访问范围、实际访问证据及展示完整程度。

CPU 不知道某个值，不等于相应 GPU 状态未恢复。原 GPU producer 已经能够正确重放，也不等于 CPU 必须算出或证明它写入的每一个字节。数据内容是否正确、指针是否属于重放地址空间、shader 是否实际访问某个候选，是三个不同问题。

### 4.2 普通数据与 GPU 地址使用不同策略

- 普通数据：恢复原初态、原 CPU 输入和原命令顺序。GPU 计算产生的数据由原 shader/API 生成。CPU 数据流分析可以帮助诊断或优化，不能成为所有 producer→consumer 链的唯一支持路径。
- 地址/句柄数据：必须有可靠的布局、typed metadata、ABI、API 记录或其他真实恢复机制。GPU 生成地址时，应确定其是否自然使用重放地址，或是否需要有明确时序的修复；不能把旧 GPU 地址当普通数值拷回后直接执行。
- 如果必须增加捕获信息，按底层布局/对象/时间点记录，避免新增按 UE 功能命名的声明。必要的 UE provider 可以提供通用 RHI/ABI 事实，不能报告“这个 pass 已验证，可以放行”。
- 不把 optional AIR 分析的成功与否直接视作上述机制的替代品。仍需 AIR/ABI 识别某个地址字段时，要说明原因、可靠边界和通用替代路径，不能伪称已完全解耦。

### 4.3 动态候选不是实际访问

无法知道索引时，可以保守恢复整组可寻址资源的身份、地址和必要状态，但要区分：

- 可能成为绑定候选；
- 确实需要恢复的原输入状态；
- 已有证据的实际 shader 访问。

“是候选”不能单独证明其全部内容都必须有 CPU 可见 producer。“没有 CPU producer 证明”也不能单独证明捕获丢了数据。若范围无法收窄，应优先使用 API/资源管理层的保守真实状态恢复，而不是无限扩充 shader 表达式来缩小集合。不能凭“可能未访问”跳过尚未恢复的非零 GPU 指针。

### 4.4 API 未定义状态、实现不支持、损坏 capture 分开

| 情况 | 处理原则 |
|---|---|
| 真实必需的创建 payload/初态缺失，地址无法重定位，引用对象已失效，必要提交数据丢失 | 保持明确失败，补捕获或恢复机制 |
| API 本来没有规定某些普通数据字节的值 | 依据具体 API 和初始化策略处理；不比较这些字节的精确值，不自动称为损坏 capture，也不伪装成恢复了原数据 |
| 合法 API 组合暂缺实现 | 标明实现缺口和通用契约，不能为维护历史负例把它改称非法 |
| 资源已恢复，仅 CPU 数值/访问展示未知 | 保留原生执行，展示 partial/unknown |
| 无法确认属于哪一类 | 先取最小证据核实，暂不全局放开；不要立即写一个“必须拒绝”的永久测试 |

API 未指定普通内容不意味着可以忽略越界、无效地址、同步或生命周期要求。原始已定义数据也不能用清零或后续快照冒充。Native 正常退出只能证明执行完成，不能独立证明应用合法或重放一致。

## 5. 下一批直接解决当前阻塞

能力名称建议为“heap backing 状态与动态绑定恢复闭环”。目标是用通用机制解决当前 UE 消费链的恢复义务；不以支持资源14714、PSO6399或某个 pass 命名实现。编号只作证据定位。

### 第一步：形成一页阻塞诊断

使用现有 capture、命令记录、API 契约和已有证据，回答：

1. 拒绝来自地址、字节初态、提交/alias、API 合法性，还是分析策略？具体判断分支是什么？
2. 当前 buffer 的 backing 出生、旧别名、CPU 输入、GPU producer、退休及消费顺序是什么？哪些是观测事实，哪些只是候选？
3. 捕获已保存哪些字节/对象事实；哪些缺失且不能从原命令再现；哪些内容本来没有 API 定义？
4. DX12/Vulkan 对应路径为什么能重放，Metal 缺的具体机制是什么？
5. 哪个实验能够证伪当前假设？结果不同会分别选择哪种实现？

一次诊断结束必须选定具体实现或可判别实验。不要把列更多可能原因当作独立完成批次。若已有证据足够，直接实施，不等更高推理模型再次批准。

### 第二步：按证据选择恢复方式

- 捕获已经包含正确状态：修复恢复映射或过强前提，避免新增冗余 readback。
- 必需帧前/别名原数据确实缺失：在 API 允许且顺序正确的边界记录真实状态，并重截一次验证。Metal 无法 raw 访问的 texture/AS 内存不得伪装成普通 heap buffer；可以用受支持的逻辑资源复制或 AS 配方恢复。
- 数据由帧内原命令生成：重放生产链和同步；普通数值不要求 CPU 证明每次写入。地址数据另行证明重放地址正确。
- 仅候选内容义务过强或 API 未定义状态被误分类：修正契约与测试，不通过猜零或删除全部 namespace 检查处理。

选择前两种以外的更复杂方案时，先说明现有 API/ABI/捕获信息为何不足。GPU 插桩、通用 shader 解释器、全新调度框架不能成为默认下一步。

### 第三步：完成最短端到端闭环

独立 native sample 复现同一 API 机制，改变 backing/offset/alias 时序/动态索引，验证修复后合法变体无需再改后端。完成必要定向检查后回 UE：先确认恢复义务满足，再在既有预算和共享锁下执行有限帧真实 GPU replay，保存输出、调度证据和失败位置。

如果仍被新问题阻止，记录它属于同类契约遗漏还是新 API 类。不能仅把拒绝位置后移称为“接近完成”。无需先实现与当前闭环无关的所有 view、格式或展示能力。

## 6. 用四个里程碑安排任务

| 里程碑 | 可交付结果 | 完成条件 |
|---|---|---|
| M1 当前恢复义务闭环 | heap/动态绑定机制、修正的拒绝依据、独立组合 sample | 同类合法变体无需增分支，真实地址/必要输入损坏可定位拒绝；当前 UE 阻塞已解除或被明确证明需要重新捕获 |
| M2 第一份真实 UE RT replay | 原生基准/捕获配置、真实 RT 执行、整帧 GPU 输出 | 在有限帧与预算内完成，输出有合理比较依据；退出0、API打开或预检通过都不能替代 |
| M3 可重复且跨场景 | 事件往返/EID0、绑定、第二份独立负载与场景变体 | 改变对象排列、尺寸/数量、帧、视角或调度组合后仍正确；声明支持范围内无需修改后端 |
| M4 对应能力开启 | 固定候选的既有最终验收矩阵、原生设备条件、开启后复验 | 满足 RAYTRACING_ENABLEMENT 的既有门槛，按对应能力开启；compute RT 不自动证明 render-stage RT |

这些里程碑不要求每个都新建一套 PHASE/BATCH 文件。仍可在现有大批次中推进，但必须在状态中明确当前处于哪一步。实现一般性问题与完成第一份真实 UE replay 交替验证，避免“先完成全部抽象”而长时间不运行实际负载。

优先级：当前闭环所必需的恢复机制 → 第一份 UE GPU 输出 → 同一机制的独立泛化验证 → 相关回归/事件可靠性 → 最终开启验收。纯展示精细度和不影响该声明范围的独立功能进入后续清单，不阻塞 M2；真实地址/必要数据恢复不得延期到运行之后。

## 7. 测试层级与负例治理

### 7.1 四层测试，避免每次小改都结算整批

| 层级 | 运行时机 | 最小有效结果 |
|---|---|---|
| T0 契约/静态检查 | 改动涉及的源码与数据格式稳定后 | 编译、格式/布局/溢出/地址映射等实际相关检查；没有必要时不额外造镜像测试 |
| T1 定向 Native→capture→replay | 实现一个恢复机制后 | 原失败的合法正例、一个独立变体、真正破坏恢复契约的负例；已定义输出及必要事件/EID0 |
| T2 能力批次集成 | 一组机制形成稳定候选后 | 少量正交组合、相关旧 capture、真实 UE 探针；先验证关键假设，再扩展验证 |
| T3 最终验收 | 准备声明/开启能力的固定候选 | 既有官方 sample、相关全套回归、UE整帧/事件/绑定、生命周期及设备能力门槛；结果必须属于该候选 |

每次测试前写明“这次会验证哪个新结论”。同一源码/二进制/输入/环境已完成的相同测试不重复。后端变化后按影响范围重跑，未重跑项标历史证据/本候选未运行；不能把旧哈希结果合成新候选全通过。捕获侧变化要生成新 capture，重放侧变化可以复用有来源记录的旧 capture。最终版本冻结后集中跑要求的矩阵，变更再次发生则按影响和既有门槛补验。

不要求每个小补丁都运行29份旧capture，也不降低最终RT开启门槛。变更触及核心恢复/生命周期时，扩大相关回归是必要工作；应记录原因和耗时，不能凭感觉把所有检查都去掉。

### 7.2 正例用机制组合验证泛化

每批选择能区分实现缺口的少量正交轴，不穷举笛卡尔积：

- 初态来源：帧前保存、创建 payload/API 保证、CPU 发布、帧内 GPU producer。
- 存储与生命周期：Shared/Private、独立/placement、同 backing 合法 alias/非重叠、背景/帧内创建。
- 地址与绑定：非零 offset、不同真实 binding slot、动态 descriptor 索引、CPU/GPU 发布。
- 执行：同/跨 command buffer、条件与动态普通计算、合法的 read-modify-write。
- 形状：同受支持格式族的不同尺寸、mip/view/subrange，以及支持范围内的 usage 组合。

在实现前保留至少一个未参与修复设计的合法组合用于验收；若它失败，修通用契约，不为其新建场景许可。加入“没有冗余 upload”“CPU 不知道数值”“可选分析不完整”正例。无需承诺任意 API 组合已全部支持，但支持范围不能由本次见过的数值列表定义。

### 7.3 旧负例重新分类

每个被保留或新增的拒绝测试记录：实际修改的捕获数据、违反的契约、预期错误类别、拒绝发生阶段。应核验 binary payload 与 XML 声明确实一致地被改变，避免 fixture 没改到真实输入。

- 结构损坏/无效身份/缺必需 payload/无法重定位地址/错误生命周期：拒绝测试。
- 合法但暂未实现的 API：能力缺口测试，不命名成 malformed。
- 合法数值、尺寸或 shader 变化：比较各自 Native 与 replay；不能要求维持旧输出或旧拒绝。
- API 未规定的普通内容：按契约处理，不对未定义字节建立逐字节 oracle。
- 展示缺少反馈：原生输出通过、展示 partial/unknown。

移除一个 dispatch/upload 不天然等于“损坏 capture”：需判断它是否造成恢复契约矛盾、无效 GPU 地址或必需输入缺失，还是变成另一个合法但输出不同/部分未定义的调用序列。更不能为维持历史 API4 预期重新引入 CPU 表达式门槛。旧失败事实保留，错误 oracle 明确作废并注明依据。

浮点/时序相关输出使用固定输入、固定帧、原生重复基准和预先确定的比较方式；只在确定性成立的范围使用 hash/逐字节相等。不得为了通过而扩大容差、关闭 RT 或比较与本次目标无关的输出。

## 8. 开发节奏、升级条件与推理分工

工作队列同时只保留一个正在闭环的能力批次，加至多两个已识别的后续依赖，避免把每个格式或 shader 症状变成独立项目。此处是任务管理建议，不授权并发代理或并行 GPU 测试。

较高推理规划负责：明确恢复契约、识别错误拒绝依据、选择通用机制、审查新限制与里程碑。Sol high 负责：按契约读对应源码、实现、必要调试/定向验证、集成并推进下一步；无需每步等规划者批准，也无需通过提高推理深度代替证据。

每轮开发使用一张简短工作卡：

| 项 | 要求 |
|---|---|
| 目标 | 一个可完成的通用行为，连接 M1–M4 中的一步 |
| 旧行为/复现 | 当前失败输入及错误类别，区分当前哈希与历史证据 |
| 契约/对照 | API 依据、DX12/Vulkan 具体数据流、Metal 差异 |
| 实现与边界 | 恢复什么、允许哪类合法变化、哪些信息缺失仍须拒绝 |
| 验收 | 一个关键正例、独立变体、必要负例、UE闭环影响及相关回归 |
| 结束记录 | 修复的根因、通过/失败/未跑、剩余新假设、候选哈希/产物链接 |

出现以下任一情况，下一步转为针对性根因审查，仍可自主继续，不自动停下来问用户：

- 连续两次相关机制修改后，同一语义阻塞未变；先证伪假设，不再机械增加邻近 sample。
- 提议新增 coverage 许可级、格式/尺寸组合、固定 binding slot、shader 名称/hash/EID 特判。
- 需要 CPU 求解新的普通数值表达式，才能允许已恢复对象上的 Native 运算。
- 新负例的唯一依据是“旧实现会拒绝”，或一个正常 Native 场景只能通过删除检查解释。
- 计划继续泛化与当前里程碑无关的能力，而关键端到端路径长期未执行。

升级审查的输出必须是一项可验证的设计决定/实验，不是重新写完整路线图。只有确实缺用户工程、权限、设备或必须由用户选择的范围时提出最小问题，并继续不依赖回答的工作。

## 9. 进度、文档与产物管理

进度只报告：当前里程碑；已消除的根因类别；真实 UE 执行到哪个阶段；独立合法组合能否无需后端改动；未证实假设；下一项能改变结论的动作。不给代码偏移/已识别 shader 数量换算完成百分比。

记录构建、定向验证、集成回归的实际耗时与资源峰值，积累两个稳定批次后再调整测试频率。不以坏 capture 数、日志数、文档页数或相同回归重跑次数作为产出指标。

当前文档治理采用小步处理：STATUS 顶部保留简短当前摘要；HANDOFF 只承载下一轮必需事实、当前阻塞和具体命令/链接；PLAN 承载里程碑；详细实验只在一份当前批次记录及 manifest。其他索引链接过去即可。遵守既有更新要求，但不再将长篇实验结果复制到每个文件。历史正文先保留，不为整理文档启动大迁移或丢弃证据。

AGENTS 和持续任务提示保持稳定原则与当前工作入口，具体 intrinsic、slot、窗口及每次新发现移入实现文档。禁止将一个尚待审查的临时拒绝提升为跨会话永远执行的规则。主对话采用本方案时，应将重复或互相矛盾的旧下一步标记为已替代；不必重写全部历史。

构建/GPU继续串行共享锁、有限帧/预算/监督，不与用户正在运行的 GPU 工作冲突。read-only 审计优先利用现有证据；无变化的失败不重复跑。中间文件、可恢复检查点和不可替代证据在外盘，仓库保留小型源码/文档/索引。清理可重建、未使用的冗余产物，保留唯一原始 capture、失败复现、稳定候选和证明索引。不 reset，不覆盖用户修改，不自动提交推送。
